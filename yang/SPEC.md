# HOSU Heat Copilot — 기술 스펙

> 기준일: 2026-08-22. 여러 API를 병렬로 탐색하면서 정보가 흩어졌던 걸 이 문서 하나로 모음.
> **이번 정리에서 JUSO 좌표제공 API와 safemap.go.kr 무더위쉼터는 스코프 밖으로 뺐다** — 승인을
> 못 받아서 지금 단계의 고려사항이 아니다(§5-F). 이후 작업은 이 문서를 기준으로 진행한다.

## 1. 개요

JunctionX Korea 2026 경북 트랙, 팀 HOSU. 폭염대응 현장인력(주민생명 지킴이 등)에게 "오늘 어느
마을부터 확인할지" 우선순위를 판정해주는 도구. 대시보드가 아니라 판정형(verdict) UX — 정보
나열이 아니라 답을 낸다. 위험도(HVI: 노출×민감도×적응능력)는 AI가 아니라 명시적 수식으로
계산하고, AI는 요약·자연어 변환에만 쓴다(재현성·감사가능성 확보).

**대상 범위: 경상북도만.**

## 2. 아키텍처 (6단)

1. 공공데이터 API (기상청, 한국사회보장정보원 등)
2. 데이터 파이프라인(Python) — 좌표 정규화·위험도 스코어링
3. 정규화 데이터 스토어(SQLite)
4. MCP 서버(Python) — `mcp_server.py`
5. AI 에이전트(Claude API) ↔ 대시보드 백엔드(FastAPI, 미착수)
6. 프론트엔드(React, 판정 UI, 미착수)

서버(MCP·백엔드)는 **로컬 호스팅으로 확정**. 발표가 팀이 직접 노트북으로 데모하는 방식이라
클라우드 배포는 하지 않는다.

## 3. 지역 필터링 — 서로 다른 두 코드 체계

같은 경상북도를 가리키는 값이라도 API마다 코드 체계가 달라서, 필터링 함수를 코드 체계별로
분리했다(`pipeline/db.py`). 하나로 억지로 합치지 않는다.

| 함수 | 대상 | 판정 규칙 | 근거 |
|---|---|---|---|
| `is_target_region(code)` | emd_code, sigungu_code, jrsdSggCd (법정동코드 계열) | `47`로 시작 | 대구(`27`)는 별도 시도코드라 자동 제외 |
| `is_target_alert_zone(code)` | 기상청 API허브 REG_ID/REG_UP | `L107`로 시작 | 실호출로 확인: 경북 산하 전부 `L107x`, 대구는 `L114`로 완전 분리 |

`require_target_region(code)`는 `is_target_region`이 실패하면 빈 결과 대신 `ValueError`를
던진다 — MCP tool이 범위 밖 조회를 "데이터 없음"으로 오인하지 않게 하기 위함.

## 4. 데이터 스키마 (`pipeline/db.py`)

중심 허브 `ADMIN_REGION`(emd_code PK)에 아래가 FK로 연결. 격자(grid_nx/ny)와 특보구역
(alert_zone_code)은 서로 다른 좌표계라 각자 컬럼으로 분리 보관 — 하나로 근사 매핑하지 않는다.

```
ADMIN_REGION(emd_code PK, sido_name, sigungu_name, emd_name,
             grid_nx, grid_ny,        -- 기상청 5km 격자 (초단기실황용)
             alert_zone_code,         -- 기상청 API허브 특보구역코드 REG_ID (특보용)
             center_lat, center_lon)

WEATHER_ALERT(grid_nx, grid_ny, announce_time, alert_type, temperature, feels_like, humidity)
  PK (grid_nx, grid_ny, announce_time)

WEATHER_WARNING(alert_zone_code, announce_time, tm_seq, title, alert_type)
  PK (alert_zone_code, announce_time, tm_seq)
  -- WEATHER_ALERT와 별도 테이블. 한 PK에 격자 기준 행과 특보구역 기준 행을 섞으면
  -- HEAT_ILLNESS에서 겪은 NULL-in-PK 버그가 재발하기 때문.

HEAT_ILLNESS(sigungu_code, occur_date, age_group, patient_count, is_death)
  PK (sigungu_code, occur_date, age_group) — 전부 NOT NULL
  -- 온열질환은 (지역,날짜,연령대)별 집계라 age_group이 PK 밖이면 같은 날 여러 연령대가
  -- 못 들어가는 버그가 있었음(수정됨).

SAFETY_TARGET(target_id PK, emd_code FK, target_count)
HEAT_SHELTER(shelter_id PK, emd_code FK, name, lat, lon, capacity, has_aircon)

WELFARE_FACILITY(facility_id PK, emd_code FK, name, facility_type, address, lat, lon)
  -- address는 원 ER 설계엔 없던 컬럼. 소스 API가 emd_code/좌표 없이 주소 텍스트만 줘서
  -- 지오코딩 전까지 원본을 보관해두려고 추가함(§5-F, 지금은 스코프 밖).

EMERGENCY_HOSPITAL(hospital_id PK, emd_code FK, name, lat, lon, available_beds)
RISK_SCORE(emd_code FK, score_date, exposure_score, sensitivity_score, access_score,
           total_score, priority_tier, nearest_shelter_id FK→HEAT_SHELTER)
  PK (emd_code, score_date)
```

## 5. 데이터 소스 현황 (재점검, 2026-08-22)

### A. 연동 완료 — 코드 있음, 실호출 검증됨

| 소스 | 파일 | 채워지는 컬럼 | 비어있는 컬럼 |
|---|---|---|---|
| 기상청 초단기실황(`getUltraSrtNcst`, data.go.kr) | `pipeline/sources/weather.py` | `WEATHER_ALERT.temperature`, `.humidity` | `alert_type`(§B), `feels_like`(§E) |
| 한국사회보장정보원 사회복지시설(`getFcltByBassInfoInqire`, data.go.kr) | `pipeline/sources/welfare_facility.py` | `WELFARE_FACILITY.facility_id/name/facility_type/address` | `emd_code`/`lat`/`lon`(§F, 지오코딩 필요 — 스코프 밖) |

두 소스 다 `DATA_GO_KR_SERVICE_KEY` 재사용(추가 신청 불필요). `unquote()` 처리 필요(인증키
Encoding 버전 이중인코딩 방지) — `_service_key()` 헬퍼로 각 파일에 구현돼 있음(현재 소스가
2개뿐이라 공용 모듈로 아직 안 뽑음).

**`welfare_facility.py`의 `jrsdSggCd` — 포항시는 구 단위 코드가 안 먹힌다(실호출로
확인).** `4711100000`(포항시 남구)·`4711300000`(포항시 북구) 둘 다 `totalCount=0`이고,
구 구분 없는 `4711000000`(포항시 전체)로 넣어야 368건이 나온다. `emd_centroid.py`의
24개 시군구명(포항시를 남구/북구로 분리)을 그대로 순회하며 이 API를 호출하는 로더를
나중에 만들면, 포항시 두 곳만 조용히 빈 결과가 될 함정 — 이 API 호출 시에는 포항시를
합쳐서 한 번만 부를 것.

| 경북 읍면동 중심좌표(정적 파일, API 아님) | `pipeline/sources/emd_centroid.py` | `ADMIN_REGION` 전체(emd_code/sido_name/sigungu_name/emd_name/center_lat/center_lon/grid_nx/grid_ny) | — |

출처는 통계청 MDIS 인구용 행정경계중심점(vuski/admdongkor 저장소, CC BY 4.0) — 신청·승인
절차가 없는 정적 파일이라 §F에서 반복된 승인대기 문제를 피할 수 있음. 경북분만 추려
`pipeline/data/gyeongbuk_emd_centroid.tsv`(417행)로 보관. 좌표계 EPSG:5179(UTM-K)를
`geo.to_wgs84`로 변환 후 격자까지 계산해서 `upsert_admin_region`으로 적재 —
`load_all(conn)` 한 번 호출로 경북 읍면동 전체가 채워진다. 안동시(4717000000) 대표좌표를
변환한 결과가 §A에서 실호출로 검증된 격자(91,106)와 정확히 일치함을 대조 확인함.

**파싱 함정(발견·수정함): "포항시 남구/북구"처럼 시군구명이 두 단어인 경우.** 이름을
공백으로 쪼개 시군구/읍면동을 나누면, 그 시군구의 대표행 자체("경상북도 포항시 남구",
3단어)에서 마지막 단어("남구")를 읍면동으로 잘못 읽는다 — 실제 하위 읍면동("경상북도
포항시 남구 구룡포읍", 4단어)과 단어 수만으로는 구분이 안 됨. `read_rows()`는 이름 대신
법정동코드 구조로 판별한다 — 코드 마지막 5자리가 읍면동+리 자리라, 전부 0이면
무조건 시군구 대표행이다(`ADMCD.endswith("00000")`). 이 버그로 처음엔 온열질환 지도에서
포항시 남구·북구 2개가 조용히 빠졌었음(§6-2 프로토타입에서 발견) — 지금은
`pipeline/sources/test_emd_centroid.py`에 회귀 테스트로 고정.

| 질병관리청 온열질환 감시데이터(§E, 사용자가 받아온 CSV) | `pipeline/sources/heat_illness.py` | `HEAT_ILLNESS` 전체 | `is_death`(원본에 없음, 항상 NULL) |

`pipeline/data/`에 원본 CSV 그대로 보관(개별 환자 단위, 2011~2025, 전국 29,763행 — 국가
API 아니라 신청/승인 개념 자체가 없음). 경북 2,500행 중 915행(37%)은 발생시군구가
비어 있어 sigungu_code를 특정할 수 없음 — 시도 전체로 뭉뚱그려 배정하면 없던 지역차를
만들어내므로 추측 대신 건너뜀(`skipped_no_sigungu`로 보고). 나이는 원본이 숫자라 10년
단위로 버킷팅(`_age_group`). 의성군 누적 43건이 초기 대시보드 시안의 "온열질환 이력
43건"과 정확히 일치함을 대조 확인 — 그 시안이 이 소스의 시군구 총계를 하위 읍면동에
그대로 복제해서 보여주고 있었다는 뜻(§7 참고).

코드 체계는 통계청 행정동코드이지만, 경북 대부분(읍/면 지역, 이 서비스가 실제로 다루는
"마을" 단위)은 행정동=법정동이라 emd_code와 그대로 호환된다. 시(市) 지역의 동(洞) 세분화
구간(포항시 남구 등)만 행정동/법정동이 갈릴 수 있음 — 지금 스코프에선 문제 안 됨.

### B. API 확정·검증 완료, 소스 모듈 구현 대기

| 소스 | 오퍼레이션 | 상태 |
|---|---|---|
| 기상청 API허브 특보현황조회(`wrn_now_data.php`) | apihub.kma.go.kr | 신청 즉시 승인, 실호출로 경북 실데이터(고령군·칠곡군 폭염경보 등) 확인함. `WRN`/`LVL`이 코드로 구조화돼 있어 텍스트 파싱 불필요. 응답이 **EUC-KR 인코딩**이라 `response.encoding = 'euc-kr'` 필요 |

data.go.kr의 옛 기상특보 API(`getWthrWrnList`/`getPwnStatus`, stnId 기반)는 격자와 안 맞고
자유텍스트뿐이라 **폐기** — 위 API허브 버전으로 교체 확정.

다음 단계에서 `pipeline/sources/weather_warning.py` 작성 예정: `authKey` 하드코드 대신
`.env`의 `KMA_APIHUB_KEY`로 분리, `REG_UP`으로 `is_target_alert_zone` 필터, `WEATHER_WARNING`
에 적재.

| 경상북도 인구·세대 통계(사용자가 받아온 xlsx, 주민등록인구통계 계열) | data.go.kr/승인 절차 없음 — 정적 파일. 검증 완료, **로더 미구현**(2026-08-23 추가, 아직 코드 없음). |

`pipeline/data/경상북도_인구.xlsx`, 4개 시트(2026-07 기준):
1. `1-1. 시도별 인구 및 세대현황` — 경북 전체 1행뿐, 안 씀.
2. `1-2. 시군별 인구 및 세대현황` — 시군 단위(23행), `HEAT_ILLNESS`의 시군구코드로 바로
   매핑 가능.
3. **`1-3. 읍면동별 인구 및 세대현황`** — **읍면동 단위(352행)**, 컬럼은 세대수·내국인
   인구(소계/남/여). "행정동 기준"이라고 시트에 명시돼 있음 — §5-A의 emd_centroid와
   같은 코드 체계 전제(경북 대부분 읍/면은 행정동=법정동).
4. **`2. 읍면동 연령별(각세) 인구현황`** — 읍면동 단위(350행) × 0~100세+ 각세 인구.
   65세 이상을 합치면 **읍면동별 고령인구비율을 실제로 계산할 수 있다** — 지금
   `RISK_SCORE.sensitivity_score`(§4)가 완전히 비어있는 상태를 채울 유력 후보. 독거노인
   가구수(어제 스코프 제외한 `ELDERLY_ALONE`)와는 다른 지표지만, 승인 없이 바로 쓸 수
   있는 고령화 취약성 신호라는 점에서 그 공백을 상당 부분 메운다.
   검증 예시: 의성군 다인면 — 각세 합계 인구 3,544명(1-3 시트의 내국인 소계와 정확히
   일치, 두 시트가 서로 대조 검증됨), 65세 이상 1,997명 → **고령인구비율 56.3%**.

**파싱 함정(미리 적어둠 — 아직 안 만들었지만 §5-A와 똑같은 종류의 실수가 날 자리다).**
행별로 명시적 코드가 없고 이름과 순서(들여쓰기 없는 계층 나열)로만 시도→시군→읍면동을
구분해야 하는데, **포항시만 예외적으로 한 단계가 더 있다** — "포항시"라는 행 자체는
읍면동을 안 갖고, 그 아래 "남구"/"북구" 행이 진짜 시군구 단위(emd_centroid의 "포항시
남구"/"포항시 북구"에 대응)이며, 그 밑에야 읍면동이 나온다. 나머지 22개 시·군은 시/군
행 바로 아래가 읍면동이라 이 특수 케이스 하나만 예외 처리하면 된다(경북에서 일반구를
가진 시는 포항시가 유일함). 이름 토큰 수로 판별하지 말고, `emd_centroid.read_rows()`가
이미 만들어둔 (시군구명, 읍면동명) 쌍 전체를 참조 삼아 매칭할 것 — 새로 추측하지 말고
검증된 24개 시군구명 목록에 기대는 게 §5-A에서 배운 교훈이다.

### C. 신청함, 승인 대기중 (data.go.kr)

- 보건복지부 응급안전안심 서비스 대상자 기본정보 → `SAFETY_TARGET`

독거노인 수(`ELDERLY_ALONE`)는 승인이 안 나서 스코프에서 제거함(사용자 지시,
2026-08-23) — 테이블·MCP tool(`get_elderly_living_alone_density`) 전부 삭제, 다시 승인
받아도 재검토 안 함.

### D. 승인됐지만 우선순위상 보류

- 국립중앙의료원 응급의료기관 → `EMERGENCY_HOSPITAL` (의도적으로 뒤로 미룸, 재개 시점 미정)

### E. 승인됐지만 필드 미조사

- 기상청 생활기상지수(4.0) — `WEATHER_ALERT.feels_like`를 API 실측값으로 채울 후보(지금은
  §6-1 자체 계산 공식으로 대체 중).

질병관리청 온열질환 감시데이터는 사용자가 CSV로 직접 받아와서 §A로 옮김(2026-08-23).

### F. 스코프 제외 (이번 정리에서 고려하지 않음 — 승인 못 받음)

- **JUSO_API_KEY**(juso.go.kr 좌표제공 검색 API) — 신청함, 승인 대기. `WELFARE_FACILITY`의
  `emd_code`/`lat`/`lon`, `geocode_address()` 완성이 여기 막혀있음.
- **safemap.go.kr 무더위쉼터**(`IF_0001`) — 키는 있는데 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`
  지속, 원인 불명. `HEAT_SHELTER` 테이블 통째로 빈 상태.
  **§A의 사회복지시설 API로 우회 불가 — 실호출로 4개 시군(안동시·의성군·구미시·포항시,
  총 979건) 확인함**(2026-08-23): "경로당/마을회관/쉼터/노인정/회관" 키워드로 찾아보면
  몇 건 걸리긴 하는데("노인복지 작은쉼터", "청소년쉼터", "포항시노인복지회관") 전부
  무더위쉼터가 아니다 — "쉼터"라는 이름의 노숙인·청소년 시설이 우연히 걸린 것뿐이고,
  진짜 무더위쉼터 지정 목록(경로당·마을회관을 지자체가 계절별로 지정)은 이 API 관할이
  아예 아니다. 재가노인복지센터·주야간보호센터 같은 정식 등록 사회복지시설만 주는
  데이터베이스라 관할 주체 자체가 다름(재난안전 계열). `HEAT_SHELTER`는 safemap.go.kr을
  푸는 것 외엔 대안이 없다.

## 6-1. 읍면동 배치 수집 & 캐싱 (`weather.refresh_all`)

시군구 23개에서 읍면동 417개로 세분화하면서 정한 방식. 실측값 기준으로 결정했다.

**격자 중복 제거로 302회.** 읍면동 417개를 기상청 5km 격자로 변환하면 고유 격자는 302개다
(27% 감소 — 도심 동(洞)들이 한 셀에 묶인다. 구미 원평1·2동 등 9개가 같은 격자). 그래서
읍면동을 순회하지 않고 `ADMIN_REGION`의 **고유 격자**를 순회한다.

**5km 격자는 우리가 고르는 값이 아니다 — 기상청이 정해놓은 좌표계다.** `geo.py`의
`_KMA_GRID = 5.0`은 해상도 설정이 아니라 기상청 격자 인덱스(nx/ny)를 계산하는 투영식의
일부다. 이걸 3.0으로 바꾸면 해상도가 올라가는 게 아니라 **좌표가 통째로 어긋난다**(검증:
서울 기준값이 공식 예제의 (60,127)에서 (71,121)로 틀어짐). 더 나쁜 건 그 틀어진 좌표로
API를 불러도 에러가 안 난다는 것 — HTTP 200에 정상 응답 형태로 `-999`(결측)가 돌아온다.
**이 방향은 재검토하지 말 것.**

그리고 3km가 있더라도 실익이 없다. 격자가 뭉치는 곳은 도심 동(洞)이고, 우리 대상인 읍·면은
이미 대부분 단독 격자를 갖는다(실측):

| 구분 | 전체 | 단독 격자 | 비율 |
|---|---|---|---|
| 읍·면 (현장인력이 실제로 확인할 마을) | 255 | 208 | **82%** |
| 동 (시 지역 도심) | 115 | 18 | 16% |

뭉치는 동(洞)들은 서로 500m~1km 거리라 3km 격자로도 어차피 안 갈라진다. 즉 5km는 이
서비스가 쓸 수 있는 사실상 최선의 해상도다.

**캐시는 별도 계층 없이 `WEATHER_ALERT` 테이블 자체다.** PK가 이미
`(grid_nx, grid_ny, announce_time)`이라 "이번 시각 데이터가 이미 있나"가 곧 캐시 조회다.
시간이 넘어가면 키가 바뀌므로 **만료 로직도 공짜** — TTL 타임스탬프나 무효화 코드가 없다.
새 테이블·새 의존성 0개.

**신선도 판정에 한 시간 여유를 둔다**(`_freshness_cutoff`). 기준시각과 정확히 일치하는지로
보면, 기상청 발표가 늦어져 직전 시각 값이 내려왔을 때 그걸 저장해도 다음 실행에서 또 미스가
나서 **매번 전량 재호출하는 캐시**가 된다. 한 시간 여유가 그 무한 재호출을 끊는다.

**HTTP만 병렬(8워커), DB 쓰기는 메인 스레드.** sqlite3 커넥션을 워커에 넘기지 않으므로
스레드 안전성 문제가 아예 생기지 않는다(`ThreadPoolExecutor`로 fetch → 결과 모아서
`executemany`). 실측 10격자 0.7초 → **302격자 약 20초** 예상.

**격자 하나가 실패해도 배치는 계속된다.** `_fetch_one`이 예외를 삼키고 에러 문자열로
반환하므로, 302개 중 1개가 죽어서 나머지 301개 성공분까지 날아가는 일이 없다. 결과 dict의
`failed`/`errors`로 보고한다.

**결측 센티널(`-999`/`-998`)은 NULL로 떨어뜨린다**(`_obs_value`). 기상청은 결측·관측불가를
에러가 아니라 **HTTP 200 정상 응답에 `-999`라는 값**으로 준다(실호출로 확인). 그대로 float
변환하면 기온 −999도가 저장돼서 위험도 계산이 조용히 망가진다 — 예외도 안 나고 화면에만
이상하게 찍히는, 제일 찾기 어려운 종류의 오염이다. 임계값 −900 이하를 전부 NULL 처리한다.

라이브 검증(2026-08-22 23시, 포항 일대 실호출): 인접 읍면동이 실제로 서로 다른 값을 냈다 —
연일읍 27.4℃ / 대보면 26.8℃ / 구룡포읍 25.7℃. 읍면동 세분화가 표시상의 차이가 아니라
실제 신호를 만든다는 확인. 2차 실행은 캐시 적중으로 네트워크 호출 0회·0.00초.

데모 준비 프리페치(ADMIN_REGION 적재 + 실황 수집을 한 번에):

```
python -m pipeline.sources.weather
```

## 6-2. 읍면동 세분화 검증 프로토타입 (`build_prototype.py`)

"실제로 카테고리별 데이터가 되는지"를 확인하려고 만든 미니 프로토타입. 지금 실데이터가
있는 두 축(기온·온열질환)만 다룬다 — 복지시설(좌표 없음)·쉼터(막힘)·독거노인(스코프
제외)은 뺐다(사용자 지시, 2026-08-23).

```
python build_prototype.py   # 약 20~30초, KMA API 최대 302회 호출(캐시 적중 시 더 빠름)
```

`prototype_map.html` 하나를 생성한다(서버 불필요, 더블클릭으로 열림). 구성:
- **종합 위험도 레이어**(기본 표시) — 읍면동 392개, `scoring.feels_like_c`로 계산한 체감온도
  기준 색상(위험/주의/양호). 팝업에 기온·습도·체감온도·해당 시군구 온열질환 누적건수를
  "상속값"이라고 명시해서 함께 보여준다 — 종류별 데이터를 합쳐서 보여주는 부분.
- **기온만 레이어** — 종합에서 등급·온열질환을 뺀 순수 카테고리 뷰.
- **온열질환 레이어** — 읍면동이 아니라 **시군구 대표좌표 24개**에만 찍는다. 읍면동
  좌표에 찍으면 실제로 없는 정밀도를 있는 것처럼 보여주게 되기 때문(§7).
- 좌측 순위 리스트(체감온도 상위 15개, 클릭하면 지도 이동).

라이브 실행 결과: 302격자 전부 성공(302/302), 읍면동 포인트 392개, 온열질환 시군구 24개
전부 표시 확인.

**만드는 중 발견·수정한 버그 둘 다 여기서 나왔다** — 둘 다 별도 회귀 테스트로 고정됨:
1. `-999` 결측 센티널(§6-1) — 3km 격자를 실험하다 발견.
2. "포항시 남구/북구" 파싱 버그(§5-A) — 온열질환 레이어에서 24개 중 2개가 조용히
   빠지는 걸 보고 발견. `pipeline/sources/emd_centroid.py`의 `read_rows()`를 코드 구조
   기반 판별로 고쳤다.

**`upsert_admin_region`은 NULL인 컬럼만 채운다** — 그래서 파싱 버그를 고친 뒤에도 이미
잘못 적재된 `hosu_heat.db`를 재실행만으로는 못 고친다. 스키마 파싱 로직을 바꿨으면
`rm hosu_heat.db` 후 처음부터 다시 채울 것(캐시는 `WEATHER_ALERT`에 남아있어도 격자
좌표 자체가 바뀌지 않는 한 재호출 없이 재사용됨).

## 7. 알려진 제약 (다음 사람이 헷갈리기 쉬운 것)

- **`get_welfare_facilities(emd_code)`가 지금은 사실상 항상 빈 배열을 준다** — 적재된
  `WELFARE_FACILITY` 행 전부 `emd_code IS NULL`(§F, 지오코딩 대기)이라 `WHERE emd_code = ?`
  조건에 아무것도 안 걸림. 코드 버그 아님, §F가 풀리기 전까지의 당연한 상태.
- `WEATHER_ALERT.alert_type`/`.feels_like`는 여전히 전부 NULL — §B/§E가 붙어야 채워짐.
- **`ADMIN_REGION`은 `emd_centroid.load_all(conn)` 한 번으로 경북 읍면동 전체(417행)가
  채워진다** — 예전엔 각 소스가 실제로 다루는 지역만 그때그때 채워지는 지연 upsert 방식이라
  안동시 정도만 있었는데, 이 정적 소스가 그 갭을 메움. 실황 수집은 §6-1 참고.
- **한 격자를 공유하는 읍면동은 같은 기온·습도 값을 갖는다** — 버그가 아니라 기상청 격자가
  5km라서 그렇다(포항시 대보면·호미곶면이 같은 격자). 읍·면은 82%가 단독 격자라 영향이
  작고, 주로 시 지역 동(洞)에서 뭉친다(§6-1 표). 격자를 더 잘게 쪼개는 건 불가능하니
  (§6-1) UI에서 "같은 값이 반복된다"는 지적이 나오면 이 이유를 설명할 것.
- **온열질환(`HEAT_ILLNESS`)은 여전히 시군구 단위 집계다.** §A의 원본 CSV 자체가 읍면동
  필드를 안 준다(개인정보/표본 이슈로 보임 — 경북 행의 37%는 시군구조차 없음). 읍면동
  화면에서 이 값을 보여줄 때는 **부모 시군구값을 상속받았다는 걸 UI에 반드시 명시해야
  한다.** 안 그러면 의성군 다인면·안계면·비안면이 전부 "온열질환 이력 43건"으로 똑같이
  찍혀서, 사용자는 그게 각 면의 실제 건수라고 오해한다(초기 대시보드 시안에서 실제로
  이렇게 나왔음 — 원인이 정확히 이거였음, §5-A에서 대조 확인). 표기 예: "온열질환 43건
  (의성군 전체)" — `build_prototype.py`(§6-2)가 이 방식으로 이미 렌더링 중.
- **읍면동별 위험도를 실제로 가르는 건 현재 기온·습도뿐이다.** 온열질환은 시군구 상속이고
  독거노인은 스코프에서 빠졌으므로(§C), 같은 시군구 안에서 읍면동 순위를 만드는 신호는
  사실상 기상 데이터 하나다. 라이브 확인으로 이 값은 실제로 갈린다(포항 연일읍 27.4℃ /
  대보면 26.8℃ / 구룡포읍 25.7℃)지만, 위험도 수식이 온열질환·취약계층에 큰 가중치를 주면
  같은 군의 읍면들이 거의 동점이 된다 — 수식 설계 시 반드시 감안할 것.
